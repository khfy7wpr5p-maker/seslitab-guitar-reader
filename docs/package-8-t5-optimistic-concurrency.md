# Package 8-T5 — Optimistic Concurrency / Stale-History Conflict

Status: **implementation candidate / not closed until PR + exact-head CI + review + exact-main CI**

## Purpose

Package 8-T5 prevents a teacher action based on an older T4 history snapshot from silently overwriting or ignoring a newer valid history state.

T5 is a pure domain-level optimistic concurrency contract. It does not introduce persistence, distributed locks, automatic merging, UI, authentication, OMR/Audiveris changes, or deployment changes.

## Core rule

Before a teacher mutation, the caller captures an immutable expectation from one exact valid history snapshot.

```text
H0 -> expectation E0

Teacher A: E0 + correction -> H1  (APPLIED)
Teacher B: E0 + correction -> H1  (CONFLICT, no partial write)
```

A stale operation never attempts to merge musical data automatically.

## Why current revision identity alone is insufficient

T4 allows a valid history-only change such as appending a teacher approval while the current revision remains exactly the same.

Therefore T5 does **not** treat only `currentRevisionId` or content fingerprint as the concurrency version.

The expectation binds:

- history identity;
- source/root-source identity;
- deterministic fingerprint of the complete immutable T4 history state;
- exact current revision ID/content fingerprint/recursive lineage fingerprint;
- revision count;
- correction-event count;
- undo-event count;
- approval count.

This means an approval-only change also invalidates an older expectation.

## History-state fingerprint

The complete already-validated immutable history plain-data state is deterministically serialized with sorted object keys and fingerprinted with the dependency-free FNV-1a 64-bit mechanism used as a version/drift token.

Prefix:

`teacher-history-fnv1a64-v1:`

This fingerprint is **not** authentication, authorization, a digital signature, or a cryptographic integrity credential. It is a deterministic optimistic-concurrency/version token used only after T4 strict history validation.

## Mutation semantics

### Fresh correction

A current expectation allows existing T2 correction creation and T4 history append. The parent is always the exact current revision read after the expectation passes.

### Fresh approval append

A current expectation allows existing T4 exact approval append behavior.

### Fresh undo

A current expectation allows existing T4 lossless undo behavior.

### Conflict

A valid but stale/mismatched expectation returns an immutable conflict result before any correction, approval append, or undo is attempted.

Conflict result contains:

- `status = conflict`;
- explicit `conflictReason`;
- exact unchanged current history reference;
- a fresh expectation for that current history;
- `revision = null`;
- `auditEvent = null`;
- `approval = null`.

No partial new evidence is produced.

Malformed/mutable/injected expectation records are invalid input and fail closed rather than being treated as a legitimate stale token.

## Required invariants

1. T5 accepts only a valid immutable T4 history.
2. Expectations are strict immutable records.
3. No ID or timestamp is generated by T5.
4. A valid fresh expectation is `current`, not an applied mutation.
5. Successful guarded mutation is `applied` and returns a new immutable T4 history snapshot.
6. Any valid intervening history change makes the old expectation stale.
7. Approval-only history changes are concurrency-visible even when current revision is unchanged.
8. Different valid evidence with identical counts/current revision is still distinguished by the full history-state fingerprint.
9. History/source mismatch is explicit.
10. Conflict produces no revision, audit event, approval, or mutated history.
11. Undo-restored content with a new recursive lineage remains a distinct concurrency state.
12. T5 does not merge, infer, or invent musical content.
13. Existing T1/T2/T3/T4 validation remains authoritative for revision, correction, approval, history, and undo semantics.

## Focused acceptance tests

Regressions cover:

- immutable deterministic expectation generation;
- `current` expectation evaluation;
- fresh guarded correction;
- two concurrent edits from one expectation: first applies, second conflicts;
- zero-partial-write conflict behavior;
- approval-only stale detection;
- different valid approval evidence with identical counts/current revision;
- undo stale detection;
- restored same content with distinct recursive lineage/history state;
- history mismatch;
- source mismatch;
- malformed/mutable/injected/forged expectation rejection;
- caller-supplied identity/time only;
- isolation from persistence/backend/UI/OMR/Audiveris/deployment wiring;
- full repository regression and production build.

## Explicitly deferred

T5 does **not** implement:

- automatic three-way merge or musical conflict resolution;
- persistent history database/API;
- distributed locks;
- retries that silently rebase a stale edit;
- accessible conflict UI — Package 8-T6;
- student sharing — Package 12;
- authentication/authorization;
- Audiveris training data — Package 8B;
- OMR/Audiveris/provider/gateway changes;
- Docker/Render/deployment changes.

## Protected boundaries

This stage must not modify:

- `backend/` OMR/Audiveris provider/runtime/preflight;
- OMR worker/provider selection;
- Cloud OMR Gateway or production OMR path;
- `Dockerfile`;
- `render.yaml`;
- current Render service/deployment connection.
