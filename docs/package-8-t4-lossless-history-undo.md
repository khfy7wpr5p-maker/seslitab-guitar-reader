# Package 8-T4 — Lossless Revision History and Undo

Status: **implementation candidate / not closed until PR + exact-head CI + review + exact-main CI**

## Purpose

Package 8-T4 adds a small, pure domain layer for preserving teacher revision history and performing lossless undo without rewriting prior evidence.

It builds only on the already-verified Package 8-T1/T2/T3 contracts.

## Required invariants

1. The automatic source revision remains immutable and is the first preserved revision.
2. Every later revision remains an immutable T1 `teacher_corrected` revision.
3. History is linear within this package and each appended revision must extend the exact current history revision.
4. Revision IDs and recursive lineage fingerprints must be unique inside one history.
5. Every non-root revision must have exactly one preserved transition event: T2 correction or T4 undo.
6. T2 correction audit events remain immutable and must bind the exact parent/result revision fingerprints and IDs.
7. T3 approval records remain immutable historical evidence and must bind an exact revision preserved in the history.
8. Undo never deletes, mutates, replaces, or re-labels an earlier revision.
9. Undo creates a new corrected revision from the current revision using the exact content of an earlier preserved revision.
10. Undo records exact current-parent, target, and result content/lineage fingerprints.
11. Restored content may have the same `contentFingerprint` as the historical target, but the undo result must have a new recursive `lineageFingerprint`.
12. An approval for the historical target does **not** automatically apply to the new undo result.
13. No identifier or timestamp is generated by the T4 domain layer.
14. Malformed, non-linear, duplicate, mutable, injected, or cross-source history evidence fails closed.

## History representation

One immutable history snapshot preserves:

- history/source identity;
- ordered immutable revisions;
- T2 correction audit events;
- T4 undo audit events;
- T3 approval records.

The history object and its arrays are immutable. Existing revision/audit/approval objects are preserved by exact reference; T4 does not clone or rewrite them.

## Undo semantics

Undo is **not** pointer mutation and is **not** deletion.

For a current history:

```text
A0 -> R1 -> R2
```

undoing to `R1` creates:

```text
A0 -> R1 -> R2 -> R3(undo content of R1)
```

`R3.contentFingerprint` equals `R1.contentFingerprint`, but `R3.lineageFingerprint` differs because `R3` has `R2` as its exact parent lineage.

Therefore an approval bound to `R1` remains historical evidence for `R1` and evaluates as non-applicable to `R3` unless a teacher explicitly approves `R3` later.

## T4 acceptance tests

Focused regressions cover:

- immutable automatic-root history creation;
- T2 correction append without overwrite;
- T3 approval preservation through later edits;
- lossless undo to an earlier revision;
- no deletion/rewrite of historical revisions;
- restored content fingerprint with new recursive lineage;
- old approval not resurrected by undo;
- exact revision lookup;
- non-linear append rejection;
- ancestor revision-ID reuse rejection inside history;
- correction evidence binding rejection;
- duplicate event/approval ID rejection;
- missing/current/no-op undo target rejection;
- mutable/injected/broken history rejection;
- forged undo binding rejection;
- cross-source/unpreserved approval rejection;
- caller-supplied identity/time only;
- isolation from persistence, OMR/Audiveris, deployment, UI, and T5 concurrency wiring;
- full repository regression and production build.
