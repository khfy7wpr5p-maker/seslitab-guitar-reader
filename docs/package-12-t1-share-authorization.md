# Package 12-T1 — Exact Teacher-to-Student Share Authorization

Status: **Implementation candidate — requires PR CI and protected-main verification before closure.**

## Purpose

Package 12-T1 introduces the first bounded sharing-domain layer after Package 8. Its only job is to keep three concepts separate:

1. exact immutable teacher revision;
2. exact teacher approval evidence for that revision;
3. explicit authorization to share that exact approved revision with one caller-supplied recipient identity.

Teacher approval alone is not sharing authorization.

## Implemented contract

`src/services/teacherShareAuthorization.js` exports:

- `TEACHER_SHARE_AUTHORIZATION_SCHEMA_VERSION = 1`
- `TEACHER_SHARE_AUTHORIZATION_STATE = "share_authorized"`
- `TEACHER_SHARE_REVOCATION_SCHEMA_VERSION = 1`
- `TEACHER_SHARE_REVOCATION_STATE = "share_revoked"`
- immutable applicability vocabulary:
  - `AUTHORIZED_EXACT_BINDING`
  - `NOT_APPLICABLE`
  - `RECIPIENT_MISMATCH`
  - `REVOKED`
- `createTeacherShareAuthorization(...)`
- `createTeacherShareRevocation(...)`
- `isTeacherShareAuthorizationRecord(...)`
- `isTeacherShareRevocationRecord(...)`
- `evaluateTeacherShareAuthorization(...)`

## Authorization binding

Authorization can be created only when Package 8 approval applies to the exact candidate revision.

The authorization records exact revision identity:

- `sourceId`
- root `sourceRevisionId`
- `revisionId`
- `revisionKind`
- `parentRevisionId`
- revision `createdAt`
- `contentFingerprint`
- recursive `lineageFingerprint`

It also records exact approval identity used at authorization time:

- `approvalId`
- approval `actorId`
- approval `createdAt`

and explicit sharing context:

- caller-supplied `authorizationId`
- caller-supplied `issuerActorId`
- caller-supplied `recipientId`
- caller-supplied/null authorization `createdAt`

No identity or timestamp is generated by the domain layer.

## Staleness and replay behavior

A later correction, undo-created revision, same-content new revision, other-source revision, revision replay with different recursive lineage, different approval record, or different recipient does not inherit authorization.

Evaluation fails closed as `NOT_APPLICABLE` or `RECIPIENT_MISMATCH` rather than widening the grant.

## Revocation

T1 adds a separate immutable revocation record bound to one exact authorization ID, source, revision and recipient.

The bounded creator requires the same caller-supplied issuer actor label as the authorization. This is only a domain consistency rule; it is not authentication.

An exact revocation evaluates as `REVOKED`. Mismatched revocation evidence never falls through to an authorized result.

## Important safety boundary

`AUTHORIZED_EXACT_BINDING` is **not** final student-delivery permission.

T1 deliberately does not:

- expose revision content;
- create a `safeToShare` or `shareAllowed` flag;
- generate public links, bearer tokens, passwords or invite codes;
- authenticate teachers or students;
- persist grants or revocations;
- add backend endpoints;
- send network requests;
- bypass quality/safety evidence;
- alter OMR, Audiveris, Render, Docker or production model configuration.

Package 12 must still add an exact-revision safety/quality eligibility boundary before any student payload can be released. Authenticated recipient access and persistence are later security/application stages and require separate architecture review if they introduce new infrastructure or dependencies.

## Required regressions

The T1 regression suite covers:

- strict immutable authorization/revocation records;
- exact revision + approval + recipient binding;
- explicit separation from Package 8 teacher approval;
- later-revision staleness;
- identical-content new revision staleness;
- cross-source rejection;
- different approval rejection;
- exact recipient matching;
- exact revocation;
- mismatched revocation fail-closed behavior;
- caller-owned identifiers/timestamps;
- mutable/extra/symbol/hidden/accessor record rejection;
- unsupported schema/state/revision-kind rejection;
- invalid domain input rejection;
- absence of content/token/final-share claims.
